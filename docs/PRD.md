> 本文档是**开发的唯一契约**。产品设计意图来源于 `艾欧泽亚因果信笺.txt`（PRD V1.3），但当二者冲突时**以本文档为准**。
> 本文档补齐了源 txt 缺失的工程规格：数据模型、判定算法、牵制消解规则、内容清单。
> 版本：E1.0（Engineering）

## 一、产品定位

网页端互动叙事解谜游戏。玩家扮演"倾听者"，阅读来自艾欧泽亚各地冒险者的求助信笺，通过**调换信件中语句块的顺序**、以及**将语句块拖到另一封信的时空锚点**，改变因果链条，影响 8 位角色的关系与结局。

**核心叙事哲学**：每个人的幸福并不总是兼容的。不存在"全员 S"的完美解。玩家不是在追求最优解，而是在无数种遗憾与成全中，寻找自己认为最值得的那一种因果。

**核心体验**：把一句豆芽时期的怯懦提问拖进导师期的庆功宴——同一句话，可以毁掉一个人，也可以拯救一个人。而有时候，你只能选择拯救其中一个。

## 四、核心机制规格

### 4.1 因果调整（基础层）

每封信由 N 个语句块构成（**N ≤ 6**），其中可拖动块 M 个（**M ≤ 4**）。玩家调整可拖动块顺序，系统按"关键节点判定法"（§5.2）结算该信的结局。

**M ≤ 4 是硬约束**——它把单封信的排列组合上限锁在 `4! = 24`，使 §5.2 的穷举判定与校验器的完备性穷举在计算上可行。任何信件不得违反。

### 4.2 跨信件拖拽

当两封信同时解锁时，可将一封信中的可拖动块拖入另一封信。跨信件拖动会同时改变**顺序**与**时空坐标**，因此同时触发 §5.2 与 §4.3。

### 4.3 时空错位判定（进阶层）

每个语句块携带原始时空坐标 `(t1, s1)`，每封信有目标时空锚点 `(t2, s2)`。令 `Δt = |t1 - t2|`（时间索引差），`Δs = |s1 - s2|`（空间枚举值序号差）。

**分类规则 —— 四种分类与源 txt §2.2 的规则表一一对应**：

```
1. (Δt == 0 && Δs == 0)  → 'reorder'    常规重排，走原判定逻辑
2. (Δt == 0 && Δs > 0)   → 'microshift' 语义微调，匹配「环境冲突」语义库
3. (Δt  > 0 && Δs == 0)  → 'transform'  语义质变，匹配「成长/回忆/传承」语义库
4. (Δt  > 0 && Δs > 0)   → 'high'       高错位，匹配「隐藏/崩坏」语义库
5. 块未被移动             → 'none'       不参与错位判定
```

> **关键：没有"自动崩坏"档位**（裁定 #8）。
>
> 源 txt 的公式 `offset >= 3 → 高错位/崩坏` 与它**自己的旗舰示例**冲突：核心体验原句是「把一句豆芽时期的怯懦提问，拖进导师期的庆功宴」，这是 Δt=3、Δs=0，按规则表属于「跨阶段同空间 = 语义质变 = 成长/回忆/传承类结局」——是游戏最好的一刻，不是失败状态。
>
> 因此规则表中「跨阶段跨空间 → 高错位 → **触发隐藏剧情或"因果崩坏"结局**」中的"或"是**真的二选一**，由各封信自行编排。「因果崩坏」是信件可选择的**结局评级 `X`**，而不是由坐标自动推导出的状态。若把它做成坐标的自动结果，游戏的核心体验就被判定引擎判死了。

**offset（= Δt + Δs）的唯一用途**：UI 呈现（涟漪强度、音效音高、虚线粗细）与排序。**不得用于语义分类，也不决定结局好坏。**

### 4.4 结局权衡（核心创新层）

三层结局结构：

| 层级 | 名称 | 说明 |
|---|---|---|
| 第一层 | 信件结局 | 单封信的排列结果，决定该场景中角色的即时关系走向 |
| 第二层 | 角色结局 | 该角色在全部信件中的倾向值累积，映射到个人最终归宿 |
| 第三层 | 全局结局 | 全部角色结局的组合 → 终章「倾听者手记」 |

**关键规则**：不存在"全员 S"的常规解。角色结局之间通过**牵制关系**相互压制（§5.4），该性质由校验器 6 穷举证明。

## 五、判定算法

### 5.1 数据结构约定

- 一切**派生状态**（角色评级、全局结局、因果树）**一律不存储**。`TendencyEvent[]` 是唯一真相源，任何状态由纯函数重新计算。这保证存档永不与逻辑不一致。
- `RankedRating`（S/A/B/C/D，可序数比较）与 `OutOfBandRating`（`X` 因果崩坏 / `echo` 回响，**不参与序数比较**）在类型层分离。禁止把 `X` 或 `echo` 塞进排序。

### 5.2 信件结局判定：关键节点判定法

**关键位置关系（KeyRelation）**是全部判定的原子。定义为对当前排列的一个可判定谓词：

| kind | 含义 | 参数 |
|---|---|---|
| `precedes` | A 排在 B 之前 | subject=A, object=B |
| `adjacent` | A 与 B 相邻（且 A 在前） | subject=A, object=B |
| `first` | A 位于首位 | subject=A |
| `last` | A 位于末位 | subject=A |
| `separatedBy` | A 与 B 之间至少隔 n 个块 | subject, object, minGap=n |
| `displacedInto` | 块 A 处于错位分类 tier | subject=A, tier |
| `carryPresent` | 排列中某块携带指定语义标签 | carry |

**判定流程** `resolveLetterEnding(letter, arrangement)`：

```
1. satisfied ← 计算当前 arrangement 满足的 KeyRelation 全集
2. 按 priority 升序遍历 letter.endings：
     若 ending.requires ⊆ satisfied 且 ending.forbids ∩ satisfied = ∅
       且 satisfied ∩ ending.requires 的元素数 >= ending.minSatisfied（默认全部）
     → 命中，返回该结局
3. 若无一命中 → 返回 letter.fallbackEnding（类型上必填，永不为 null）
```

**保证**：
- `Letter.fallbackEnding` **在类型定义中必填**，因此函数签名不可返回 null——"所有组合都有结局"由**类型系统**保证。
- 校验器 4 进一步断言：**没有任何可达排列会落到 fallback**。fallback 是类型安全网，不是设计出路。

### 5.3 角色结局追踪

每封信结算后，为每个涉及角色写入 `TendencyEvent`：

```
TendencyEvent {
  letterId, characterId,
  delta: number,      // 通常 -2..+2
  reason: string,     // 人类可读的解释，用于 UI "关键选择记录"
  order: number       // 写入序，用于确定性排序
}
```

角色倾向值 `= Σ delta`。角色结局 = 在 `character.endings` 中找 `trigger` 命中的那一条：

```
type EndingTrigger =
  | { kind: 'tendency'; min: number; max?: number }   // 倾向值区间映射
  | { kind: 'special'; conditionId: string }          // 独立触发器（用于 X / echo）
```

`X`（因果崩坏）与 `echo`（回响）**只能**通过 `special` 触发器获得，从不参与倾向值区间映射——这直接落实裁定 #6：小星的 X 结局不需要追踪引擎做任何特例。

### 5.4 结局牵制引擎

**牵制边定义**：

```
ConstraintEdge {
  id, from, fromMinRating, to, delta: -1 | -2, allowedMax?, rationale
}
```

- 边只存 `delta`（降级幅度），**永不存目标评级**（裁定 #2 的直接落实）——写死目标评级会在内容调整时产生悬空引用。
- `allowedMax` 可选，表示"不得把对方压到比此更低的等级"。

**消解算法** `resolveConstraints(ratings, edges)`：

```
输入：初步角色评级 ratings（来自 §5.3）
1. 共存结局检测（§5.5）：命中的共存条件 → 豁免其指定的边，并直接授予指定评级
2. 未被豁免的边，按固定顺序排序：
     sort by ( |delta| 降序, declarationIndex 升序 )
3. 单趟顺序处理，每条边最多触发一次：
     if ratings[edge.from] >= edge.fromMinRating:
        newRating = clamp(ratings[edge.to] + edge.delta, floor = allowedMax)
        ratings[edge.to] = min(ratings[edge.to], newRating)   // 只降不升
4. 返回 ratings 与 ResolutionTrace[]
```

**确定性 / 终止性 / 可解释性证明**：
- **终止**：评级**单调不升**。边 `e` 的触发条件 `from >= fromMinRating` 在评级下降后只会更难满足，绝不会因处理某条边而让新边变为可触发。故单趟处理即收敛，无震荡。
- **确定**：排序键 `(|delta|, declarationIndex)` 全序（声明序唯一），故结果与遍历顺序无关。
- **可解释**：`ResolutionTrace` 逐条记录"哪条边、因谁触发、把谁从什么降到了什么、rationale 是什么"，UI 因果树直接消费。

> **双向牵制（裁定 #5）的落地**：「小星S→铁壁B」与「铁壁S→小星B」同时存在时，两条边都进入排序。若排序靠前者把对方压到 `fromMinRating` 之下，后者即静默失效——这就是"结果唯一"的来源，也是玩家观察到"我先成全的那个人，最终压住了另一个"的机制根源。

### 5.5 共存结局

共存结局是"让两个看似矛盾的结局同时成立"的隐藏解，**优先于牵制引擎执行**。

```
CoexistCondition {
  id, name, involvedCharacters,
  requires: KeyRelationId[] 或 跨信件错位条件,
  exempts: ConstraintEdgeId[],   // 豁免哪些牵制边
  grants: { characterId, rating }[]
}
```

| 共存结局 | 涉及角色 | 触发条件 |
|---|---|---|
| 「双向奔赴」 | 小星 S + 铁壁 S | 将小星导师期语句拖入铁壁豆芽期信件，形成"未来的继承人回应过去的引路人" |
| 「隔空和解」 | 烈风 S + 月见 S | 将烈风导师期语句拖入月见成熟期信件 |
| 「时间之外」 | 夜语 S + 铃兰 S | 将两人导师期语句互换，形成"你教我的，我教给了未来的你"的因果闭环 |

校验器 7 断言：三个共存结局的触发条件在数据上**真实可达**（由穷举求解器验证，不接受人肉断言）。

### 5.6 全局结局：倾听者手记

由四个维度决定，**由角色结局组合纯函数推导**：

| 维度 | 定义 |
|---|---|
| 成全指数 | 获得 S/A 评级的角色数 |
| 牺牲指数 | 因他人高评级而被降至 C/D 的角色数 |
| 平衡指数 | 角色结局是否形成均衡（S/A 与 C/D 数量接近） |
| 因果倾向 | 玩家更倾向牺牲自己成全他人，还是让各人自担后果（由 `TendencyEvent.reason` 分类统计） |

手记文本按维度分档从模板表选取。校验器 9 断言：**全部可达的角色结局组合都能映射到非空手记文本**。

## 十、术语词典规格

8 个分类：高难副本、战斗机制、职业与角色梗、社交系统、生产采集、房屋与幻化、RP 与社区、游戏梗。收录总量约 60~80 条，逐条来自源 txt §8.1。

**条目结构**：

```
GlossaryEntry {
  id, term, pinyin, category, brief, detail,
  example, linkedCharacterIds, relatedTermIds, memeRef?
}
```

**黑话使用三原则**（源 txt §7.3）：语境优先（只出现在玩家对话，旁白保持通用语言）、可理解性（首次出现轻量注释）、角色差异化（老玩家用得多，豆芽用得少，RP 玩家用"世界内"语言）。

**渐进式引入**：按章节分布——第一章高难副本，第二章社交系统，第三章生产/房屋，第四章 RP 社区，终章游戏梗串联。

## 十一、校验器清单（质量保证）

`npm run validate` 全量执行。每条都是 Vitest 断言。

### 引用完整性
1. 所有 `letterId`/`characterId`/`termId`/`statementId` 引用真实存在，无悬空引用
2. 信件文本中标记为黑话的词，词典中必有对应条目
3. 词典条目的 `linkedCharacterIds` 所指角色，必须在正文中真的使用过该术语

### 结局完备性
4. 每封信的**全部可达排列**都命中已写结局，**无任何排列落到 fallback**
5. **不存在不可达结局**：每个已定义结局至少能被一种排列达成
6. **不存在"全员 S"路径**：穷举全局求解，断言无法同时让 8 位角色都拿到 S/A
7. 三个共存结局的触发条件真实可达

### 逻辑自洽
8. 牵制图确定性：结果唯一、可解释、无震荡
9. 角色结局组合 → 手记文本全覆盖，无组合落到空文本
10. 阶段可达性：信件引用的角色阶段不得早于该章已解锁阶段

### 节奏与连贯
11. 戏份配额：每角色相邻两次出场间隔 ≤ 2 章，总出场次数 ≥ 阈值
12. S 级铺垫：任何 S 级角色结局，其关键选择在 ≥ 2 封信中被铺垫
13. 难度曲线单调：判定复杂度按章节非递减
14. 新机制前置：用到的错位档位必须是该章已解锁能力

## 十二、技术栈与合规

**技术栈**：Vite + React 19 + TypeScript + dnd-kit + Zustand + D3 + LocalStorage + Vitest

**美术音效**：零外部素材。角色头像用 SVG 抽象纹章；音效用 Web Audio API 实时合成（音高随错位档位变化）；视觉用 CSS 渐变与滤镜。

**合规**（源 txt §7.1）：不使用 FF14 官方 IP，专有名词（角色名、地名）做模糊化处理；不映射真实玩家 ID 或具体事件；术语词典按社区通用释义收录。
